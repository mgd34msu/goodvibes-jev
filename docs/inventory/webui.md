# Web UI inventory: goodvibes-webui to products/webui

Every tracked file of goodvibes-webui (608 files, from `git -C ~/Projects/goodvibes-webui ls-files`), read in full, with its disposition and every check it makes. Nothing is dropped unless it is specific to WRFC or QEMU; the intent document's DROP call for the permission mode sheet and `lib/permission-mode` is void per the owner ruling of 2026-09-26, so those files carry JEV and become the gate presets sheet. No file in this product is WRFC- or QEMU-specific, so there are no DROP rows.

Read, understand, choose (owner ruling 2026-09-27): each row names every check its file makes (each list, set, regex, pattern table, cutoff or threshold, lookup, comparison or classification whose result decides what the code does next), with its line, what it decides and how it decides it today, and the choice made on that reading. A check that answers a question of meaning with a guess becomes a Jev reading, named by pattern and battery; a check stays code only with the concrete reason it is not a guess (id equality, arithmetic, a size or limit the program sets, a grammar a machine produced, a closed enum the daemon or this program writes, a value the owner configured, exactly what the user typed). A category label (deterministic, fixed format, security, display only, renders already-judged state) is never the reason to keep a check as code, and a blanket conversion is never the reason to make one a Jev reading: redaction, sanitizers, pairing and step-up, card and secret detection and format detection get the same reading as everything else. No heuristic is kept behind a Jev reading, not even as a backup, and what a site does when Jev cannot answer is left to the owner.

Where old code tests a closed union the daemon or this program produces with substring or prefix tolerance, the row keeps the check as code and states that the port matches the closed values exactly, so no heuristic survives there either. Every check chosen as a Jev reading also appears in its section's decision-point table (Where, Guessed today, Replaced by). A test file's assertions are not checks: its row lists the checks its helpers and fixtures make and says whether its expectations move because the code under test moves to a Jev reading.

Every file that renders old WRFC-loop state (fleet review verdicts and acceptance checklists, best-of-N attempt judging, the workstream tree and its task graph) is JEV as a view of the contract tree: the value it shows comes from the contract runner's Jev batteries (docs/inventory/wrfc-to-jev.md). Docs that describe the permission mode surface, the workstream view or WRFC are JEV because they are rewritten for the replacement. The UI is not redesigned: every screen, panel, command, style and interaction keeps its look; a Jev reading replaces only the decision.
