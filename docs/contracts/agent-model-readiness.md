# Agent model-readiness readings

THE14 / THE63 D1698–D1708 migrate semantic adequacy from the Agent's point tables to two canonical engine routing batteries. These are read-only judgments, not authorization or hosting attestations.

## Owners and output

`agent.models.route-readiness` reads latency, context window, tool support, vision, cost and privacy independently, plus third-party cloud transfer and a separate vision question for each recipe example. `agent.models.local-recipe-fit` reads overall recipe fit and memory adequacy from immutable hardware facts, recipe requirements and actual detection evidence. Both are registered once in `routing/judgment-registry.ts`, exported by `routing/index.ts`, and composed by typed engine helpers.

The battery definition owns the only dimension weights and score/level bands. No provider-name, recipe-name, RAM cutoff, latency cutoff or capability-flag point table computes adequacy. True settled zero scores remain zero. Missing, low-confidence, held, rejected, deferred and unavailable readings have nullable scores and levels; they never become a middle score, a zero-score substitute or a default winner. Results carry dimension outcomes/confidence, decision IDs and requested/reported judgment model provenance. Those model fields are not attestation of hosting or locality.

The Agent applies factual missingness and mechanical availability after composition. Unknown window/tool/vision/cost/provider evidence stays unknown even if a synthetic reader returns a high rating. A latency measurement must be successful, tied to the exact route and measured provider identity and accompanied by a valid timestamp; a provider-wide statistic, quality benchmark composite or saved winner is insufficient. Registered provider facts must include hosting/endpoint/documentation evidence before a cloud-transfer or privacy claim can be published. A localhost endpoint alone does not prove no onward transfer. An unavailable or explicitly unconfigured provider/model cannot become ready through a favorable judgment.

Recipe examples have no implicit capability metadata. Names containing “vision”, “vl” or “multimodal” do not establish image input. A recipe's generic name, detected stack or benchmark winner does not establish the exact served model's context, latency or privacy. Recipe readiness remains deferred until those facts exist, while a settled recipe-fit reading can still be shown and used for explicit-null fit ordering. There is no 0.72/0.28 fit blend.

## Complete-source and lifetime boundary

Registered and raw `models` / model harness entry points inspect the complete original invocation before argument translation. The registry JSON preflight refuses hidden object data and non-index/sparse array structure rather than dropping it before the product projector; raw model capture includes hidden object fields and rejects non-index/sparse arrays. Translation retains the exact original admission closure and options identity. The inspection owner captures original catalog models, current route, favorites, provider/endpoint definitions, artifact descriptors and full benchmark metadata, relevant configuration and published health/serving snapshots before any semantic preview or truncation. Published plain provider DTOs are captured completely. Actual registry adapters use an explicit owned facts boundary: names, advertised capabilities, model-source provenance, endpoint and hosting/setup declarations are data, while credential/client internals and transport functions are excluded. Adapter models getters are never invoked; the captured registry catalog supplies model facts. Provider object and trusted `isConfigured` method identities are checked before that method can be called again. Credential-only internal booleans are not the provider’s overall configured state.

Supported native Maps are converted by exact string keys; accessors, proxies, cycles, unsupported instances and oversize input are refused before serialization. Large collections are screened in complete value/path-framed batches under the unchanged owner limits (40,000 characters and eight parts per source, at most 128 sources and one million characters overall). Every batch must settle unchanged before a reading can run; strings are never split to evade screening. Oversized individual values and over-budget collections hold. No field preview, pre-redacted error or hash is a substitute for screening original semantic evidence.

Only a current, settled, unchanged protected-source projection permits a battery/port acquisition. Redacted or malformed projections hold the whole result instead of returning original fields. Freeform provider errors are not part of the readiness rubric or output. Where complete health snapshots contain them, their originals still cross the source boundary before any derivation.

Receipts remain alive through the consuming output construction. Every await, transport attempt, judgment log and result publication checks admission, cancellation, session/owner, provider API and registry, configuration, artifact/read-model sources, captured source contents, authoritative context limits, battery, port, requested model, ask function and recorder. The installed recording backend may have its pre-existing trusted model getter; its entire prototype chain and slot descriptors are captured and checked before re-reading, so late accessor/proxy replacements are refused without invocation. Untrusted source DTO accessors remain forbidden.

The registered model read projector marks only its mechanically resolved inspection dispatch as read-only result publication. The registry retains its consumed admission check through final cleanup, then retires it; there is no reusable callback or new body authority. Explicit execution/write tools and settings mutation evidence cannot opt in, while mixed state-labelled tools must resolve a read in their trusted projector. Failing cleanup still returns its projection capacity slot exactly once.

Acquired backend guards are retained across nested reads and through the last awaited source/projector release; a completed inner read cannot escape a later backend swap. A fresh invocation has a fresh guard set, including when callers reuse an argument object. Late cancellation or any replacement discards the result. Each protected handle has one idempotent release path, including cancellation and errors. Dedupe is scoped to one inspection; there is no cross-call readiness cache.

## Startup and hard boundaries

`localModelCookbook` stays synchronous and facts-only for first-render detection and setup posture. It publishes deferred enrichment, nullable scores and no unearned recommendation; startup performs zero readiness judgments. Explicit model inspection uses the asynchronous enrichment path. Unknown scores are never coerced to zero or used to recommend “Start with Ollama”; setup plans cannot claim ready-to-try without settled evidence.

The raw hardware profile contains CPU, RAM, platform, architecture and accelerator hints, not a RAM-tier judgment. Existing `core/hardware-profile.ts` byte arithmetic and 80% VRAM / 60% RAM headroom remain unchanged, as does the cookbook's 32 GB starter download-size choice. Static instructions, recipe ID dispatch, endpoint/protocol/private-address checks, resource guards, smoke/install/apply confirmations and route-change permissions are preserved. Neither inspection nor a favorable reading downloads a model, starts a server, probes an endpoint, changes a provider or applies a model.

## Verification and limits

Offline tests use deliberately counter-table readings through real model status/route/local consumers, exact admission/cancellation wiring, missing/failed/unrelated evidence, source/owner/backend replacements, malformed or protected source, and no-judgment startup. Scripted local screening fixtures are not live calibration or evidence of real provider behavior. Live semantic accuracy, cost and latency acceptance remain open.

The existing global privacy floor can classify a 13-digit numeric epoch timestamp that happens to pass Luhn as card-shaped material. This slice deliberately preserves that fail-closed behavior: such an artifact is held with no score or data release. A schema- and provenance-aware timestamp treatment requires a separate reviewed contract; there is no generic numeric/PAN exemption here.

Excluded: D1709–D1711 model free-text search, `localStackFor` identity, benchmark-prompt recognition, provider-error redaction and model-family adoption. No remaining name regex is treated as verified privacy evidence.
