# Native work ledger (read-only)

Use `/work <exact-daemon-project-id>` to select the native project owned by the configured authenticated daemon. `/work` reopens that selection. With no selection it first tries passive `projectPlanning.status` with empty input on the authenticated host. This uses the existing `read:knowledge` grant only. Discovery denial or failure is explicit, and a work-ledger-only token can use `/work <exact-daemon-project-id>` directly. `/panel open work` opens the same modal. A missing project, endpoint or exact-origin TUI credential is reported as unavailable. The project ID is never derived from a workspace path or legacy planning data.

The Work, Intent, Attention and Evidence tabs show native stable work/attempt IDs, work and criteria revisions, goals, criteria, attention reasons, evidence targets and references. `reportedState complete` and `verificationState verified` are different facts. Evidence history labels its historical outcome; current verification comes only from the host projection. Old planning approvals do not grant native execution authority.

Visible status and cursor values update without a keypress. After a host/authentication replacement, the first ready snapshot replaces the loading view automatically. Later added or removed rows retain the interaction-frozen layout with an explicit notice; an arrow key reveals the new layout. Long native facts scroll line by line and rewrap on resize.

This view uses the supported `WorkLedgerReadBinding` / `WorkLedgerReadClient` and public `operator-read-client` transport. It creates no ledger store, database, authority, mutation action or native runner. Existing Planning and contract surfaces and data are unchanged. Authentication uses only the TUI-owned credential bound to the configured exact HTTP(S) origin. The daemon-global operator token, Agent private credentials and unbound environment tokens are never native fallbacks. Opening a reader never mints, copies or repairs credentials. See [TUI host pairing](host-pairing.md) for explicit owner-terminal setup.

Host/workspace replacement requires a fresh explicit project selection. Credential, home or saved pairing-state replacement invalidates the prior reader, discovery, pending mutation preflight and queued intake permits. Subscription starts before snapshot; coalesced notifications trigger durable history catch-up rather than advancing a cursor themselves. Errors clear displayed data; close and reopen reconnects. The modal's identity boundary also discards frozen rows immediately after disconnect, revocation or replacement.

The evidence tab keeps the latest 500 caught-up events plus current projected evidence. The transport's bounded history limits still apply; an oversized initial history is reported unavailable rather than silently truncated into a fabricated current state. Selection is session-local. The host must implement the native project-bound snapshot/history operator routes; this consumer does not provision that host or start native execution.

## Interactive host credential boundary

The live TUI owner may use `/host pair --bootstrap-shared --apply` to review a host-bound administrative credential and answer a fresh exact phrase. This uses the same TUI-owned store, resolver and pairing core as the standalone terminal route. Generic, model, harness and nested command dispatch cannot authorize the mutation. `/pair` still means companion/WebUI pairing. See [host-pairing contract](host-pairing.md) for cancellation, hidden-prompt invalidation, durable uncertainty and saved-but-unverified recovery. Pairing does not establish provider, workspace, Jev, admission or execution readiness.
